# P7 source-to-registry implementation

Status: IMPLEMENTED and OFFLINE_TESTED. No actual BuildKit/Skopeo process, real OCI
push, OSM authentication/publication, infrastructure installation or service restart
was performed. The approved worker, registry, tools and research OSM identity remain
live prerequisites. The previous P6 image-push software gap is addressed by this
source change; P5/P6 reports remain historical evidence, not current feature lists.

## Publication mechanism

`telecom.registry.Publisher` invokes maintained Skopeo rather than implementing an
OCI upload protocol. It accepts a validated single-platform OCI archive and an exact
repository/digest. Publication is restricted to enabled server-owned tenant entries
with scope DISPOSABLE_RESEARCH_REPOSITORY, authentication_required=true and an exact
repository allowlist. Fully qualified canonical names prevent Docker short-name
normalization to an unintended destination. No request can choose a tool, executable path, shell, TLS bypass,
mutable tag, foreign-layer URL or arbitrary credential file.

The purpose `registry-publish` and exact repository bind the private JSON secret
reference. Its value is a JSON-encoded object containing username and password.
An owner-only temporary auth.json contains the encoded credentials. They never
appear in argv, inherited environment, journal/report fields or persisted tool logs.
An isolated child HOME contains a private registries.conf and empty snippets directory,
so host mirrors and credential helpers are not inherited. Signature policy defaults
to reject and allows only the local OCI transport and exact destination namespace.
The policy term insecureAcceptAnything concerns unsigned-image acceptance, not TLS:
copy/inspect both explicitly require TLS certificate verification. Signature trust,
SBOM and malware analysis are not claimed by digest verification.

Skopeo runs with a pinned version, no transfer retries, one parallel layer copy,
--preserve-digests and OCI media type. The destination is repository@sha256, never a
mutable tag. Raw registry manifest readback must hash to the expected digest AND
match local manifest bytes exactly. The local archive's manifest/config/layer sizes
and SHA256 values are checked before any client invocation. Foreign/external layer
URLs and unsupported media types are rejected.

Duplicate publication uses the tenant/repository/digest receipt: a VERIFIED receipt
skips copy but performs fresh readback. SUBMITTING/VERIFYING/UNKNOWN_OUTCOME blocks
automatic replay. Interrupted writes are never assumed absent or successful. No
partial upload is deleted and no registry repair/garbage collection is attempted.
An uncertain outcome requires operator read-only investigation; automated uncertain
receipt reconciliation/resume is not implemented. This favors blocked promotion
over duplicate or unverified side effects.

## Bounds and diagnostics

- Existing client process-group supervisor: 256 MiB sampled process-tree RSS,
  bounded output and cancellation cleanup. No host Docker/containerd fallback.
- One publication deadline: <=60 seconds, including version check, copy and readback.
  Each client also receives its command timeout; retry count is explicitly zero.
- Max archive 128 MiB; manifest/config <=1 MiB; publication <=32 layers. Registry
  output is bounded to 1 MiB and diagnostic lines to 64 KiB. All Skopeo temporary
  writes are directed under the sampled 130 MiB disk watchdog.
- Only uncompressed OCI TAR archives are accepted. Ordinary headers and PAX
  timestamp metadata are supported (16 KiB per header, 64 KiB total). PAX path/size
  overrides, GNU/sparse extensions, compressed outer archives and malformed sizes
  fail before TAR library metadata allocation. Verify exporter compatibility before
  live activation.
- A version-pinned debug-trace observer stops at <=256 configured observed HTTP
  requests; missing trace evidence fails closed. It rejects plaintext HTTP traces.
  Raw traces are discarded in memory. These counts are observed client request
  traces, NOT independently measured wire counts. Redirects/internal tool traffic
  and sampling overshoot must be bounded/certified against the selected client and
  registry/proxy logs before enabling live use. No exact wire-quota claim is made.
- Watchdogs are sampled, not kernel hard quotas. A dedicated bounded filesystem and
  worker/coordinator limits remain required. Python archive validation has a bounded
  multiple-of-128-MiB memory cost, separate from the 256-MiB child watchdog.
- Diagnostics persist stage/code/exit status and enum classifications for TLS/auth/
  digest/request-budget failures. Arbitrary registry/server messages are suppressed.

## Worker identity and trust boundary

The existing off-host TLS BuildKit design remains. Its contract now explicitly
requires CPU millicores (1..1000), memory MiB (1..1024), PID count (1..128), disk MiB
(1..2048), client duration (1..120 seconds), finite worker lease (1..120 seconds),
quota evidence and DEDICATED_OFF_HOST_QUOTA_ENFORCED isolation.

Before context transmission, Python performs verified mTLS to one operator-pinned
IPv4 address, checking expected hostname and reviewed peer certificate SHA256.
Buildctl then uses that pinned IP plus --tlsservername and the dedicated worker CA.
No DNS lookup/rebinding is needed. Loopback, link-local, unspecified and configured
protected CIDRs are rejected. TLS files are bounded and the private key owner-only;
encrypted keys cannot trigger interactive password prompts. The worker CA must be
dedicated to the approved worker. Identity preflight and Buildctl use separate TLS
connections; server identity/CA stability is part of worker certification.

Worker endpoints and registry repository names currently use IPv4/hostname and
HTTPS default port 443 for registries; custom registry ports and IPv6 are not
supported by the existing manifest/repository schema.

The controller cannot prove remote cgroups, lease expiry or network policy from a
configuration declaration. Independently certify them and retain evidence before
activation. Untrusted Dockerfile commands run only on that disposable worker. No
host socket, kubeconfig, OSM credential, registry-publication secret, host entitlement,
SSH forwarding or build secret is supplied. Private base-image authentication is
not implemented. Source-pinned metadata does not guarantee reproducible output:
pin base images/dependencies and restrict remote ADD/frontend/network access.

## Durable release and promotion flow

Jobs persist ACQUIRING, VERIFYING_IMAGE, BUILDING, ARTIFACT_VERIFIED,
PUBLISHING_IMAGE, REGISTRY_VERIFIED, PACKAGING, VALIDATING_PACKAGE,
PACKAGE_VALIDATED and COMPLETED, or a terminal FAILED/CANCELLED/INTERRUPTED outcome.
Registry receipts persist intent before copy and exact verification afterward.
External I/O is outside SQLite transactions. Host-wide/per-workload/publication
locks remain nonblocking. No automatic worker, polling loop or retry is installed.

Only successful readback proceeds to package preparation. The verified digest
replaces scalar values.image in the captured chart; identical captured values are
rendered and archived. Release records retain initial job ID, stage lineage,
source/image/package identities, receipt reference and deployment-disabled status.
Repeated identical content preserves the first immutable release/history.

Catalog request AND actual publication recheck registry evidence. Built-image
receipts must be VERIFIED, <=300 seconds old, match repository/digest and current
enabled tenant registry policy. Previously sealed P5 built releases with NOT_RUN
publication are denied. Prebuilt-image releases retain full existing registry
content verification. Changed policy, stale or failed receipt blocks promotion.
A catalog request is still explicit; no Git event or build automatically publishes
packages or deploys an instance. Instance upgrades/rollback remain NOT_VERIFIED.

## OSM preparation without CLI

The existing osm_catalog.Catalog handles verified HTTPS authentication, POST package
content, UUID identity and exact readback. It has no osm/osm_im dependency. The real
research branch now rejects default passwords and admin/root usernames, authenticates
against the configured research project UUID, and GETs that UUID to verify its name
and identity before package lookups or POSTs. Scope is still restricted to
research-<tenant>. Real account role/RBAC certification is a live prerequisite; a
non-admin username alone does not prove least privilege. No production credentials
or catalog entries were used. Offline tests exercise the NBI branch with osm_im
unavailable and verify policy rejection before authentication.

## Dashboard

Nine views include Registry Publications. Jobs show Git/build/digest/publication/
validation states and failure reasons; releases carry initial job lineage and
registry receipt references. Catalog publication requests and independent approval
remain separate from deployment approval. UI explicitly states that deployment
approval is required and instance execution remains disabled. Existing Selector,
monitoring and the research-only launcher are reused, without production activation.
