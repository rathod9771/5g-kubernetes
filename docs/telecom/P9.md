# P9 complete researcher orchestrator and CI/CD integration

## Scope and implementation boundaries

P9 completes the external researcher CI/CD loop that P1–P8 left with a
create-only OSM adapter: onboard your own RAN/Core, push a new source
revision through the same pipeline, and apply or roll back a verified
revision against an already-running disposable instance. It adds one new
module, `scripts/telecom/upgrade.py` (`InstanceUpdate`), and does not modify
the existing P1–P8 adapters: `InitialDeployment` (create-only), `Lifecycle`
(frozen, fail-closed, unrelated design sibling) and `Pipeline.request`'s
pre-existing `action='update'/'rollback'` stub (still `NOT_VERIFIED`, still
covered by its own existing test) are all untouched.

`InstanceUpdate` is a second, independent request/approve/submit/refresh
adapter bound to an existing `WORKLOAD_READY` deployment and an
already-catalog-published release of the *same* workload. Every guardrail is
real and offline-testable: independent reviewer approval (one-use, 300s TTL,
exact content-hash binding to both the request and the unchanged deployment),
the same shared lifecycle lock used by catalog publication and initial
create (so no two lifecycle-mutating operations ever run concurrently),
pending-OSM-operation conflict detection, pre-submission and post-submission
Kubernetes image-digest/readiness verification, rollback restricted to the
immediately prior deployed release only, a stale-source-revision guard
(an "update" may never target a release older than the one currently
running — only a rollback may move backward, and only one step), durable
bounded history (64-entry retention on both the request and the deployment's
`release_history`) and no automatic retry after an `UNKNOWN_OUTCOME`.

Live execution stays off by construction: `submit()` additionally requires
`deployment_targets[tenant].upgrade_rollback_certified is True`. No shipped
policy ever sets this field — it exists only so a human can flip it, once,
after a separately approved disposable OSM v19 update/rollback test (see
P9-LIVE-TEST.md) confirms the exact NBI update-operation shape on this
installed backend. Until then every real environment's `submit()` call fails
closed with `NOT_CERTIFIED`, before any OSM request is sent, exactly
mirroring how `InitialDeployment` itself was OFFLINE_TESTED long before any
disposable live test ran. The offline demo (`demo_upgrade.py`) sets this flag
only inside its own private, throwaway fixture policy object; it is never
read from any file, environment variable or shipped configuration.

An unapproved request (still `AWAITING_APPROVAL`) can be cancelled by its
owner at any time: nothing has been sent to OSM at that state, so
cancellation is unconditionally safe and simply blocks any future approval
of that specific request.

## Researcher walkthrough (continuing from P8)

1. Complete P8 onboarding through `WORKLOAD_READY` (see P8.md). Record the
   deployment id (the same id returned by `deployment-requests`).
2. Prepare a new source revision through the existing pipeline exactly as for
   onboarding: `POST /pipeline-jobs` → `POST /pipeline-runs` → a new sealed,
   `VERIFIED_PACKAGE` release of the *same* workload.
3. Publish that release to the catalog exactly as in P7/P8:
   `POST /publication-requests {action:"catalog"}` → independent reviewer
   `POST /publication-approvals` → `POST /catalog-publications`.
4. `POST /instance-update-requests {deployment_id,publication_id,action,event_id}`
   with `action` one of `"update"` or `"rollback"`. Rollback is accepted only
   when the requested release is exactly the deployment's immediately prior
   release (its `release_history[-1]`); an update is rejected if the
   requested release predates the one currently running.
5. Independent reviewer `POST /instance-update-approvals {request_id,event_id}`.
   An unapproved request may instead be withdrawn with
   `POST /instance-update-cancellations {request_id,event_id}`.
6. Operator `POST /instance-updates {request_id,approval_id}`. This always
   fails closed with `NOT_CERTIFIED` unless the tenant's deployment target has
   been separately certified (see above); it is never certified in a shipped
   configuration.
7. Operator `POST /instance-update-observations {request_id,event_id}` —
   bounded one-shot status refresh, exactly like `deployment-observations`.
   `WORKLOAD_READY` durably updates the deployment's current release and
   appends the previous release to `release_history`; any other outcome
   leaves the deployment's recorded running release unchanged.
8. `GET /instance-update-requests` and `GET /deployments` show full durable
   history, including `release_history`, for operator review.

## Remaining limitations

Exact OSM v19 NS-update NBI operation shape (`updateType`, field names, the
resulting `lcmOperationType`/status strings) is UNVERIFIED and must be
confirmed by the disposable test in P9-LIVE-TEST.md before certification;
mismatches fail closed exactly as the create path already does. Rollback
eligibility is deliberately limited to one step back; there is no multi-step
rollback, no automatic rollback-on-failure, and a `FAILED` or `UNKNOWN_OUTCOME`
update never mutates the deployment's recorded running release. Application
health and telecom-protocol verification remain `UNVERIFIED`/`NOT_RUN`
exactly as in P8; `production_eligible` is always false.

## Reproducible offline demonstration

    PYTHONPATH=scripts PYTHONDONTWRITEBYTECODE=1 python3 -m telecom.demo_upgrade --output /tmp/p9-demo-unique --helm /usr/local/bin/helm.real

Onboards a disposable fixture to `WORKLOAD_READY`, produces a second release
of the same workload from a bumped chart revision (no BuildKit — the image is
unchanged; only chart content differs, which is enough to exercise release
identity, catalog publication and the update/rollback machinery end to end),
applies it as a guarded "update", then rolls back to the original release.
All OSM/Kubernetes I/O is an explicit in-process fixture; `production_calls`
is always 0 and `upgrade_rollback_certified` is set only in the demo's own
private policy object.
