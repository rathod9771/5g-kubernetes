# P5 execution implementation and verification

P5 extends, rather than replaces, P1–P4. No service was restarted, no live GitHub,
registry, BuildKit or OSM endpoint was contacted, and no workload/catalog change
was made. Local Git/Helm and disposable child processes are real offline executions.
No commit or push is authorized.

No row is LIVE_VERIFIED. A content-verified image is not evidence of RAN/Core
functionality or production qualification. The existing qualification gates remain
false for simulated protocol evidence. Instance execution is intentionally incomplete
until installation-specific OSM operations and trusted rollout readers are certified.

## Execution and identity

`execution.py` reads a pinned SHA into a fresh, config-free bare Git repository.
Local objects are confined beneath a server-configured tenant workspace, with
alternates and object symlinks rejected. Checkout hooks, filters and submodule
recursion never execute. Public GitHub URLs must match an exact server allowlist;
only HTTPS github.com is accepted, with redirects/credential helpers/prompts disabled.
Source archives reject traversal, links, devices, excessive files/depth/expansion.
Uncommitted files are excluded. Linked Git worktrees/private GitHub/LFS materialization
and submodules are not supported. LFS pointer files remain repository bytes, not
fetched large objects; such projects need a reviewed acquisition extension.

Every command has a deadline, 256 MiB process-tree RSS watchdog, output cap,
process-group cleanup and minimal environment without inherited credentials.
Git command deadlines are 30 seconds each; archive/output limit 16 MiB. Fetch
objects have a sampled 16 MiB disk watchdog. These are watchdogs, not hard disk
quotas; a dedicated bounded filesystem remains necessary for adversarial workloads.
Only trusted Git/BuildKit client binaries run locally. Dockerfile RUN executes on
an explicitly provisioned off-host TLS worker, never the host Docker socket.

Server policy must attest a dedicated quota-enforced worker, bounded execution
lease (1–120 seconds) and client deadline (1–120 seconds). The client cannot certify
remote quotas, egress or lease expiry itself: validate these before activation.
Client cancellation terminates local process groups/disconnects BuildKit. A
partition or SIGKILL requires the worker lease to terminate remote work; no remote
cleanup success is inferred. Foreground worker SIGINT/SIGTERM records interruption
and cleans up local children. Hard-killed jobs remain non-QUEUED and cannot replay.

Build output is an OCI layout, whose actual manifest/config/layer hashes and sizes
are checked. A tool exit code or claimed digest alone cannot succeed. Single Linux
amd64 builds are currently supported. OCI image/reference verification also accepts
declared amd64/arm64 when content agrees. Image cap is 128 MiB; metadata and layer
counts are bounded. A digest-addressed registry read verifies all referenced blobs;
no redirects, challenge forwarding or automatic login/retry is performed. Registry
credentials are owner-only server secret references bound to tenant, purpose and exact destination, not request
passwords. One 30-second registry budget covers successive requests (a read begun
near deadline can finish within its bounded socket timeout). Dockerfile private-base
registry auth, multi-platform manifests and image registry push are not implemented.
Built OCI exports are retained privately by digest, not loaded into host containerd.
Retention uses an fsynced temporary file and atomic create without overwrite; existing
archives are reverified and corrupt archives fail closed.
Storage has a bounded inventory/512 MiB prospective retention check; operator retention is needed.

For build charts the supported contract is scalar `values.image`. Only that value
is rebound to the verified image reference. The same captured values are rendered,
validated and archived, so packages cannot silently retain a different image.
The release records source/archive hash, image digest/platform, package digests,
worker quota-evidence reference and state history. Reproducibility metadata does not
prove a reproducible build: base images/dependencies/network must be pinned/reviewed.

`pipeline.py` persists QUEUED -> ACQUIRING -> VERIFYING_IMAGE -> PACKAGING ->
COMPLETED or FAILED/CANCELLED/INTERRUPTED. A host-wide execution flock and per-workload
flock prevent overlap. Every transition is audited; external I/O occurs outside
SQLite transactions. Repeated delivery IDs return the original queued job, never
rerun a finished job. Different payload with the same ID fails. Failed/interrupted
jobs cannot automatically retry. A new explicit event needs operator investigation
where external outcome is uncertain. No background worker or retry loop is installed.

## Catalog and lifecycle

Catalog targets come only from owner-only server policy. Publication requires a
verified P5 package, independent reviewer, exact target/package/request binding,
300-second approval expiry, publisher role, lifecycle lock and durable SUBMITTING
intent before network I/O. Only enabled `DISPOSABLE_RESEARCH_PROJECT` targets named
`research-<tenant>` are accepted. Credentials must be limited to that disposable
project on a test OSM installation; the adapter reuses `osm_catalog.Catalog`
authentication, UUID validation, HTTPS and exact read-back verification. Shared
transport responses are now capped at 16 MiB. No schema changes were introduced.

Both names are checked before POST. Existing names conflict, never PUT/overwrite;
updates use a new versioned package identity. Successful catalog update therefore
means a new immutable revision, not mutation of an in-use catalog object. A failure
is conservatively UNKNOWN_OUTCOME, including auth/preflight failures; no POST is
retried and no partial object is deleted. Two package POSTs are not transactional.
Project-exclusive credentials are required to avoid an external name-creation race;
flock is not distributed fencing. A crashed SUBMITTING record stays blocked and
needs manual read-only reconciliation. No automatic repair is implemented.

Instance requests and `lifecycle.py` retain NOT_VERIFIED, reject protected NS IDs,
require known tenant/cluster/namespace ownership for planning, distinct versioned
rollback artifacts, fresh context and no pending operation. Caller claims cannot
enable execution. Execute always fails closed until the OSM upgrade/rollback
backend, trusted Kubernetes image/generation/rollout verification and telecom health
checks are certified. There is no terminate/delete/retry fallback and no live
rollback eligibility claim. This is an explicit remaining functional limitation.

## APIs and researcher workflow

Existing simulation endpoints remain available and labeled. Additional authenticated
endpoints beneath `/api/telecom`:

- GET `pipeline-jobs`, `publication-requests`: tenant-scoped histories.
- POST `pipeline-jobs`: workload_id, chart, event_id, optional pinned commit,
  image_mode (`prebuilt` or `dockerfile`), optional registry secret_ref.
- POST `pipeline-runs`: job_id; explicitly executes exactly one queued job.
- POST `pipeline-cancellations`: job_id,event_id; durable cancellation request.
- POST `github-webhooks/<workload_id>`: native GitHub push JSON, delivery/event
  headers and SHA256 HMAC. Server policy binds subject/tenant/repository/ref/chart;
  no bearer token is needed on this one signed ingress. It only queues a job.
- POST `publication-requests`: release_id, action (`catalog`,`update`,`rollback`),event_id.
- POST `publication-approvals`: request_id,event_id; independent reviewer.
- POST `catalog-publications`: request_id,approval_id; explicit publisher action.

Registration uses the existing schema-v1 manifest and capability validation. In the
research dashboard choose Register, Queue, Run, inspect Jobs/Releases, Request,
Approve and Publish. Update/rollback requests show NOT_VERIFIED. This is a JSON
contract interface, not a complete source editor or deployment wizard. Existing
RAN Selector/monitoring pages remain linked. Token storage is memory-only, there is
no continuous polling, and UI timeout never means an uncertain job is safe to repeat.
For longer builds prefer the foreground worker, then refresh job history manually.

## Reproducible offline demonstration

```sh
cd /home/rclab/5g-kubernetes-cicd
export PYTHONPATH=scripts
python3 -m telecom.demo_execution --output "$(mktemp -d /tmp/p5-demo-XXXXXX)/run" --helm /usr/local/bin/helm.real
```

This creates a disposable external RAN Git repository, captures its actual commit,
verifies a valid empty OCI fixture, runs real Helm validation, prepares exact KNF/NSD
archives, exercises approval/readback against an explicit catalog simulator,
checks duplicate events and audit integrity, and records a blocked update request.
The OCI fixture is pipeline data, not a working gNB. Registry and catalog transports
are SIMULATED; Dockerfile build and telecom protocols are NOT_RUN. Runtime databases,
OCI/package archives and secret fixtures stay under /tmp, outside Git candidates.

Implementation references: [Docker OCI exporter](https://docs.docker.com/build/exporters/oci-docker/) and [GitHub webhook signature validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries). These specify client behavior and do not certify this installation.
